Model decision

One child is the product. More children add context.

Recommended: a switcher, not a roster. Parents move into one clearly named child’s context; the dashboard never presents sibling progress as a comparison table.

Recommended · switcher

At one child, the switcher disappears and the student’s name anchors the entire surface. At two, two named choices appear. At four, all four names remain available in the same compact control; no dashboard grid grows four columns wide.

Why: depth matters more than comparison. Every action is tied to the selected child, reducing the risk of praising or pressuring the wrong student.

Rejected · roster

A roster is useful for a parent managing four children, but it makes the one-child experience look like administration. It also invites sibling comparison, which is not a product goal.

At four children, the selected-child switcher remains the same interaction. The current student name is repeated in the action card and progress panel.

Effort without exposure

Parents can see work happening without seeing failure.

Effort signals separate absence from struggle. They stay broad enough that no parent can infer a private score or an individual failed attempt.

01 · Activity

Active 5 of the last 7 days

Shows a stable pattern without revealing minute-by-minute time-on-task.

02 · Focus

Working on Algebra, level 3

Names the current learning area so the parent understands direction, not performance.

03 · Clearance

Last cleared: Badge 2

Only passed milestones travel upward. No score, attempt count, or wrong answer appears.

Cooldown treatment: the parent sees active days, the current topic, and the last cleared badge. No “failed exam” label appears. The gap reads as continued work rather than stalled progress.

State coverage

Every visit stays factual and calm.

The document state controls render the product states directly. Loading, empty, error, and offline are included so the parent never sees a blank dashboard.

No student invited

Empty state with one action: Add a student. No fake progress or extra machinery.

Invited, never logged in

Invitation is waiting, resending is one tap, and the parent knows what appears after first sign-in.

Logged in once, then stopped

Last activity is stated plainly, without blame or a fabricated task.

Active and clearing levels

Activity pattern, current focus, last cleared badge, and remaining climb are visible.

Active but clearing nothing

Effort stays visible; absence of a new clearance is not framed as failure.

Mid-cooldown

Shows continued effort and the last public milestone. The failed exam remains private.

Badge just earned

Gold is reserved for the new cleared badge and the changed progress state.

Account cap

Explicitly a limit on the account, with one review action and no judgement of ability.

Multiple children

Use the named switcher at two and four children; never compare siblings in the overview.

Offline / failed load

Last known state remains readable offline. A failed request gets a retry, not a blank shell.

Gap list

Open product decisions are visible.

These gaps are not improvised into the screen. They need product or backend decisions before Flutter implementation.

  • Parent child-switcher componentThe system has Tabs and Select, but not a named parent child-context component. Confirm the final reusable variant, selected-state announcement, and four-child overflow behavior.
  • Effort-signal data contractDefine the activity window, timezone, stale-data threshold, and how “active day” is calculated without exposing granular time-on-task.
  • Account-cap request workflowThe visual state is defined, but the backend route, review SLA, and parent-facing request confirmation are not yet specified.
  • Invite resend / reshare behaviorConfirm whether resend generates new credentials, how many resends are allowed, and which share channels are supported.
  • Offline cache policyDefine which parent fields may remain on-device, when they expire, and how the app labels stale information.

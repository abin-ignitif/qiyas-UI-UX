Recovery proposal

Parent-mediated recovery keeps a student from being stranded.

A student created without an email has no independent reset channel. The product should make the stuck state explicit while the parent approves a fresh credential.

Student sees

“A reset request was sent to your parent. You’ll receive a new code after approval.” The request state has a visible pending label, a cancel route, and no promise of an instant reset.

When approval arrives, the student returns to the same screen with a new one-time code step. The typed identity is preserved.

Backend contract required

  • Parent identity and approval scope
  • Request expiry and abuse limits
  • One-time credential issuance and expiry
  • Notification channel and delivery status
  • Audit trail for a minor’s recovery request
Do

Keep the student’s known identity, explain the wait, and preserve the route back to work.

Don’t

Invent an email reset path for students who do not have an email address.

Gap list

  • Parent-mediated recovery backendApproval, expiry, notification, abuse limits, audit trail, and fresh credential issuance are not defined.
  • Native biometric enrollmentPlatform labels, availability, failure, and secure-storage behavior need a Flutter contract.
  • Persistent-session securityDefine session lifetime, device binding, logout behavior, and what shared-device switching clears.
  • Invite expiry and credential formatDefine whether the invite issues a password, one-time code, or link and how the student requests a refresh.

Experience difference

Parent signup is careful and bounded: reason, verify, set up, invite. Student sign-in is fast and forward: known identity, one credential, optional unlock, then work. The difference comes from fewer fields, fewer decisions, and persistent state — not from playful decoration.

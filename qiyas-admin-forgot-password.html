Admin authentication · Qiyas

Recover access with a code, not a magic link.

A four-step admin recovery flow — email, verify code, new password, success — inside the same unauthenticated shell as sign-in. Every failure state names what happened, why, and what to do next, keeping typed values and focusing the first invalid field. Definitions the system does not carry are recorded as gaps, not invented.

Recommended Applied

A visible page selector 01–04 that shows real step content and stays synchronized with Back and Continue on both canvases. The six-cell OTP group auto-advances, supports backspace-back and full-code paste, and the resend line is a real countdown.

Rejected Not built

Magic links, security questions, social or SSO recovery, second-factor enrollment, celebration states, and any invented password policy beyond the three visible rules.

Live preview

Four pages, two canvases.

The document page selector and the Back and Continue controls inside each canvas stay synchronized across both previews. Mobile and desktop are independent clones, so editing one never resets the other; theme and locale switching never resets the active page.

Step gallery

The four pages, at a glance.

Selecting a page number shows that page's real content. Page state is a prototype navigation aid and is not automatically a production component.

01

Email

Eyebrow, heading, description, an LTR email field, the primary send action, and a ghost route back to sign-in. Format validates on blur only.

02

Verify code

Six 48×48 OTP cells, a masked destination, a real resend countdown, the primary verify action, and a ghost route to a different email.

03

New password

New and confirm password fields with reveal, a live three-rule checklist, mismatch on the confirm field, and the primary reset action.

04

Success

Confirms the reset and states the next step. One Ink primary action returns to sign-in; there is no celebration.

States

Every way recovery can go.

Failure copy follows what happened, why, and what to do next. Validation runs on blur for format, live for password rules, and on submit for server errors — never on untouched fields.

Default / filled

Empty and ready states for each page. Labels stay visible; placeholders never replace them.

Wrong code

What happened: the code did not match. Why: it may be mistyped. Next: re-enter or resend. Entered digits stay in place.

Expired code

What happened: the code expired. Why: too much time passed. Next: request a new code without retyping the email.

Resend cooldown

A real countdown disables resend until it reaches zero, then becomes an active Resend code button.

Rate limited

Too many attempts; the countdown uses mono tabular figures and never mirrors in Arabic.

Offline

Distinguished from a server response; typed values are unchanged and retry is offered.

5xx / timeout

Names the failure or the timeout, then offers retry. Values are preserved.

Password mismatch

Inline on the confirm field: the passwords do not match; use the same value in both fields.

Weak password

The live checklist shows unmet rules with an icon and text, never colour alone.

Submitting

Every primary action disables with aria-busy and a pending indicator; no double submit.

Gap list

Open decisions stay visible.

Per the gap-list convention, nothing here was invented to make the flow look finished.

  • Admin second factor / SSO

    Undefined in the system. Only the emailed code is shown; no authenticator, recovery-code, or identity-provider surface is designed.

  • Admin account provisioning / activation

    How an admin account is created, invited, and activated — and whether recovery is even available before activation — has no designed surface.

  • Admin session lifetime and device policy

    Session length and idle lock are unspecified; this flow ends at the sign-in surface.

  • Admin role resolution

    Super admin versus organisation admin is resolved after authentication; the recovery flow is role-agnostic and the post-login landing surface is undefined.

  • Audit logging requirements

    What recovery events are logged, retained, and exposed to the operator is not defined.

  • Password policy source of truth

    The three visible rules (8 characters, one number, one uppercase letter) are shown as a checklist; the authoritative policy and its enforcement point are unconfirmed.

  • Email delivery and resend contract

    Delivery provider, code lifetime, resend cooldown value, and anti-abuse thresholds are unspecified; the UI shows a countdown without promising a fixed window.

Guardrails

Do and Don't.

The recovery surface stays quiet, truthful, and provisioned-only.

Do
  • Keep one Ink primary action per page.
  • Preserve typed values and entered digits in every failure state.
  • Keep codes, timers, and emails LTR-isolated with tabular figures.
  • Keep Back and Continue synchronized with the page selector.
Don't
  • Add magic links, security questions, or social recovery.
  • Invent second-factor enrollment or SSO.
  • Add celebration states, gold, or gradients.
  • Validate untouched fields or promise a fixed code lifetime.
